# 知识库管理系统设计：六框架 × LLM Wiki

日期：2026-08-13  
状态：设计已逐节确认，待用户审核书面版本

## 1. 目标

把当前以 Markdown 存储和主题索引为主的 Obsidian 知识库，升级为一套由人和 AI 共同维护、能够持续沉淀和复用的知识管理系统。

第一阶段以 Obsidian 为主要操作界面，建立目录、元数据、索引、日志、工作流、权限与巡检机制；第二阶段再开发独立可视化后台。两阶段共用同一套 Markdown/YAML 数据，不进行二次迁移。

系统采用六个业务框架：

1. 项目
2. 资产
3. 资源
4. 辅助
5. 灵感
6. Skill

底层借鉴 Andrej Karpathy 的 LLM Wiki 模式：原始来源、LLM 维护的 Wiki、约束 Agent 的 Schema 三层分离；新增来源不只是保存，而是被持续编译进相关主题页、索引和知识关系中。

## 2. 设计原则

### 2.1 唯一主归属

每篇正式笔记只属于一个主框架。跨框架关系通过 YAML 关系字段和 Obsidian 双向链接表达，不复制多份文件。

### 2.2 来源、结论和推断分离

- 原始来源保真，不由 AI 覆盖修改。
- 外部输入归入资源，不直接视为系统结论。
- AI 推断必须标注依据和可信度。
- 已确认结论、推断和待核实信息不得混写为同一可信等级。

### 2.3 人负责定性，AI 负责维护

AI 可以自动执行：

- 新建笔记；
- 补充元数据；
- 更新索引和日志；
- 查重和建立链接；
- 生成归属建议；
- 更新项目摘要；
- 生成知识健康报告。

以下动作必须由用户确认：

- 移动现有文件；
- 改变笔记的唯一主归属；
- 将普通成果晋升为资产；
- 将方法笔记晋升为 Skill。

### 2.4 先形成运行机制，再建设界面

第一阶段不开发独立后台。先让 Obsidian 中的数据结构、状态流转、索引和 AI 操作稳定运行；未来后台只读取相同 Markdown/YAML，提供看板、筛选、关系图和审批界面。

## 3. Karpathy LLM Wiki 的本地化架构

### 3.1 来源层：Raw Sources

保存文章、报告、视频、网页、会议记录、原始数据、WorkBuddy 文件等输入。

规则：

- 保留原件或可追溯地址；
- 不用加工笔记替代原始来源；
- 原始来源原则上不可修改；
- 来源缺失或失效时在资源笔记中标记，不静默删除证据链。

### 3.2 Wiki 层：六框架

六框架是知识库的业务导航和正式知识层。AI 负责持续更新页面、交叉引用、摘要和关系。

### 3.3 Schema 层：知识库操作手册

由仓库内的 `AGENTS.md` 和 `00-系统` 中的规则文件共同定义：

- 六类边界；
- YAML 字段；
- 摄取、查询、回写和巡检流程；
- 资产与 Skill 晋升标准；
- AI 自动权限和人工确认边界；
- 索引、日志和待确认队列的维护规则。

## 4. 六框架定义

### 4.1 项目

承载有明确目标、进度、下一步和验证过程的工作。

生命周期：

`筹备 → 进行中 → 等待/受阻 → 已完成 / 暂停 → 归档`

项目完成后仍保留在项目框架内，不整体移入资产。项目中的可复用成果可以经确认晋升为资产；稳定方法可以经确认晋升为 Skill。

### 4.2 资产

用户已经加工、确认并拥有复用价值的成果，例如：

- 报价方案；
- 脚本终稿；
- 客户调研档案；
- 交付模板；
- 对外方案；
- 经确认的案例。

资产必须有明确版本、确认人和来源项目。未经确认的成果只能作为资产候选。

### 4.3 资源

外部输入与证据，例如：

- 文章；
- 报告；
- 视频拆解；
- 网页；
- 课程笔记；
- 原始数据；
- 会议和访谈原始材料。

资源必须保留来源信息，不直接作为已确认结论。

### 4.4 辅助

支撑工作执行的材料，包括：

- 模板；
- 检查清单；
- 提示词；
- SOP；
- 工具说明。

辅助不保存 Agent 运行日志或系统配置，也不自动参与成果晋升。

### 4.5 灵感

保存尚未验证的想法、机会、假设和连接。

状态流：

`待整理 → 待验证 → 已进入项目 → 已采纳 / 已放弃`

灵感进入项目后仍保留原始笔记和决策依据；放弃时记录原因，避免重复思考。

### 4.6 Skill

保存已经验证、可被人或 AI 重复执行并产生稳定结果的方法包。

一个 Skill 至少包含：

- 触发条件；
- 适用范围；
- 输入；
- 明确步骤；
- 输出；
- 验收标准；
- 至少一次验证记录；
- 失败和边界说明。

普通方法笔记只有在满足标准并经用户确认后才能晋升为 Skill。

## 5. 知识生产链

核心转化链为：

`资源（外部输入） → 灵感（待验证想法） → 项目（推进验证） → 资产（确认成果） → Skill（稳定方法）`

这不是强制每条内容依次走完的流水线，而是常见的知识演化路径：

- 资源可以直接支持已有项目；
- 灵感可以长期保留，不强制立项；
- 项目可以产生多个资产和多个 Skill；
- 资产与 Skill 必须保留来源关系；
- 辅助横向支持所有阶段，但不自动成为资产或 Skill。

## 6. 目录结构

```text
知识库根目录/
├─ 00-系统/
│  ├─ 知识库首页.md
│  ├─ index.md
│  ├─ log.md
│  ├─ 待确认队列.md
│  └─ 健康报告.md
├─ 01-收件箱/
├─ 10-项目/
├─ 20-资产/
├─ 30-资源/
│  └─ raw/
├─ 40-辅助/
├─ 50-灵感/
├─ 60-Skill/
├─ 90-归档/
└─ Templates/
```

仓库根目录还应包含 `AGENTS.md`，作为 Agent 进入仓库后优先读取的操作规则。

每个正式框架包含一个 `Index.md`。框架内部不预设大量主题子目录；主题主要通过 Index、YAML、标签和双向链接组织，只有附件或规模明显增长时才建立必要子目录。

## 7. 元数据设计

### 7.1 公共字段

```yaml
---
id: KB-20260813-001
title: 虎客科技技术客服 AI 副驾
type: project
status: active
created: 2026-08-13
updated: 2026-08-13
owner: 李大谱
confidence: confirmed
source_refs: []
related: []
review_date: 2026-08-20
---
```

公共字段回答五类问题：

- 身份：`id`、`title`；
- 唯一主归属：`type`；
- 当前状态：`status`、`updated`、`review_date`；
- 可信程度：`confidence`、`source_refs`；
- 知识关系：`related`。

### 7.2 可信度

- `confirmed`：用户确认或有直接证据；
- `inferred`：AI 推断，正文中必须说明依据；
- `unverified`：尚未核实，不可直接作为对外结论。

### 7.3 类型扩展字段

项目：

- `goal`
- `next_action`
- `deadline`

资产：

- `asset_type`
- `version`
- `approved_by`
- `derived_from`

资源：

- `source_type`
- `source_url`
- `author`
- `published`

辅助：

- `helper_type`
- `applies_to`
- `version`

灵感：

- `hypothesis`
- `decision`
- `project_ref`

Skill：

- `skill_status`
- `trigger`
- `inputs_outputs`
- `validation`

收件箱允许字段不完整。只有正式进入六框架的笔记才需要通过元数据校验。

## 8. 核心操作

### 8.1 双入口

- 用户明确归属的内容可以直接进入对应框架；
- 不确定、临时或杂乱输入进入 `01-收件箱`；
- AI 整理收件箱时补元数据、查重、建立关系并给出归属建议。

### 8.2 摄取

1. 读取新增资料；
2. 提取关键事实、观点、证据和待验证项；
3. 查询 Index 和相关页面，检查重复与冲突；
4. 生成唯一主归属建议；
5. 新建或更新相关 Wiki 页面；
6. 更新相关框架 Index 和全局 `index.md`；
7. 在 `log.md` 追加摄取记录；
8. 涉及移动、改归属或晋升时写入待确认队列。

一个来源可以更新多个页面，但只保留一份主来源。新信息与旧结论冲突时应显式记录，不静默覆盖。

### 8.3 查询与回写

1. 先读全局 `index.md` 和对应框架 Index；
2. 读取最相关页面和来源引用；
3. 回答时区分已确认、推断和待核实内容；
4. 若查询产生具有长期价值的新比较、分析、方案或连接，提出回写建议；
5. 用户同意回写后，新建或更新笔记，并同步索引、关系和日志。

### 8.4 晋升

资产候选条件：

- 已形成完整成果；
- 已被用户确认；
- 有明确复用场景；
- 有版本和来源关系。

Skill 候选条件：

- 触发条件明确；
- 输入输出明确；
- 步骤可执行；
- 验收标准明确；
- 至少有一次验证记录。

AI 只生成候选并写入待确认队列，用户批准后才移动文件或改变主归属。

### 8.5 巡检

每周轻巡检：

- 收件箱积压；
- 到期复查；
- 没有下一步的进行中项目；
- 待确认队列；
- 长期未处理的灵感。

每月深巡检：

- 页面之间的矛盾；
- 被新来源取代的旧结论；
- 孤立页和缺少入链的页面；
- 重要但缺少独立页面的概念；
- 缺少来源或可信度的结论；
- 重复页面和版本漂移；
- 资产或 Skill 晋升候选；
- 可通过新来源填补的数据缺口。

## 9. 索引、日志与待确认队列

### 9.1 `index.md`

内容导向的总目录。每个页面包含：

- 链接；
- 一句话说明；
- 类型；
- 状态；
- 可选的更新时间或来源数。

AI 查询时先读总索引，再进入框架 Index 和具体页面。

### 9.2 `log.md`

按时间追加，不改写历史。统一标题格式：

```text
## [YYYY-MM-DD] ingest | 标题
## [YYYY-MM-DD] query | 问题
## [YYYY-MM-DD] promote | 候选或批准事项
## [YYYY-MM-DD] lint | 巡检范围
```

日志只记录操作摘要和影响页面，不保存冗长聊天流水。

### 9.3 待确认队列

每条待确认事项包含：

- 动作类型；
- 当前文件；
- 建议主归属或目标路径；
- 建议理由；
- 受影响链接；
- 风险；
- 用户决定；
- 执行状态。

## 10. 现有知识库迁移

由于仓库已有大量内容和未提交修改，迁移分三阶段完成。

### 阶段 1：建立骨架

新建目录、规则、模板、Index、log、收件箱、待确认队列和健康报告。现有文件保持原位，不批量移动。

### 阶段 2：建立映射

扫描现有内容，生成迁移建议清单：

- 当前路径；
- 建议主归属；
- 建议目标路径；
- 分类理由；
- 可能冲突；
- 资产候选或 Skill 候选；
- 受影响的双向链接。

此阶段不自动移动。

### 阶段 3：逐批迁移

用户逐批确认后，AI 执行移动，并在同一批次中：

- 修复双向链接；
- 更新 Index；
- 更新 YAML；
- 更新日志；
- 检查重复和断链；
- 用 Git 保留可追溯历史。

## 11. 第一阶段交付范围

第一阶段包含：

- 目录骨架；
- `AGENTS.md` 知识库操作规则；
- 全局首页、Index、log、待确认队列和健康报告；
- 六个框架 Index；
- 通用模板及六类模板；
- 元数据与状态规范；
- 收件、摄取、查询回写、晋升、巡检工作流说明；
- 现有文档分类映射报告；
- 基础结构校验脚本或等价检查机制；
- Obsidian 中可直接使用的导航和查询入口。

第一阶段不包含：

- 独立 Web 后台；
- 向量数据库或复杂 RAG；
- 未经确认的大规模旧文件移动；
- 全自动资产/Skill 晋升；
- 将聊天流水和运行日志批量导入正式知识层。

## 12. 第二阶段预留

未来可视化后台直接读取现有 Markdown/YAML，提供：

- 项目看板；
- 资产目录与版本；
- 资源与证据链；
- 灵感漏斗；
- Skill 目录和验证状态；
- 待确认审批；
- 健康报告与关系图。

稳定的 `id`、`type`、`status`、关系字段和日志格式是后台接口的基础。

## 13. 验收标准

设计实施完成后应满足：

1. 从知识库首页可进入收件箱、六框架、待确认队列和健康报告；
2. 新笔记可通过模板进入系统，并拥有唯一主归属；
3. AI 能按规则执行沉淀、查询回写和巡检；
4. 每次摄取会更新 Index 和 log；
5. 已确认、AI 推断和待核实内容可被明确区分；
6. 资产与 Skill 不会未经确认自动晋升；
7. 现有文件在用户确认前不被批量移动；
8. 迁移建议能列出理由、风险和受影响链接；
9. 不存在因第一阶段改造而产生的明显断链或重复副本；
10. Markdown/YAML 可被未来后台稳定解析。
